⚠ Not built yet — spec below, one hard constraint identified

The iNat photo bank (117,670 photos / 7,364 classes) currently plays two roles at once: it is the prototype source for the unseen route, and every proxy script that scores a "which leg helps" question queries against those same prototypes. A validation set needs to break that loop or every measurement leaks.

The mistake this avoids: if a held-out query photo was itself averaged into its own class prototype, the leg would score near-perfect and every weight sweep since v37 would look better than it is — this is exactly the "gold-only proxy read +31.75, inflated" trap already hit once (§ HANDOFF, v37 build note) and the "+31.75 → +12.08" correction on the same page.

Proposed build (not yet run): for the ~6,398 unseen-route classes with ≥2 iNat photos, hold out 1 query photo per class; classes with exactly 1 photo can't validate this way and stay proto-only. Candidate space for scoring must include the ~5,200 uncovered classes as distractors — an iNat-covered-only candidate space is the same "gold-only" inflation in a different shape. Estimated eligible val set: a few thousand photos across ~5–6k classes, one query each.

Honest ceiling on this proxy: it validates the iNat-proto leg against iNat's own photo distribution — not eval-image shift. Per the transfer chart above, even a proxy built this carefully should be treated as directional, not as a real-score prediction, until anchored against an actual submission.

Why "CLIP-style" and "softmax cross-entropy" are the same statement here: CLIP-style means the softmax class-weight matrix is replaced by frozen text embeddings instead of a learned linear head. That's exactly this loss — Sunghan's answer and 류's clarification both describe the identical mechanism, just from two ends.

One real deviation from vanilla CLIP: temp=30.0 is a fixed scalar, not CLIP's own learned logit_scale (normally clamped to ln(100)≈4.6). Worth flagging since it's exactly the s term CosFace needs (see below) — it's already sitting there as a hyperparameter, not something to add.
류.正.열 — "Option 1: each pair vs all negatives, sim matrix N×C (C≈35k for FishNet)? Or Option 2: negatives within the mini-batch only, N×c (c≤32)?"  오성한 — "I implemented option 1."
✓ Option 1 confirmed — one number needs correcting

Option 1 is correct: logits = temp * (f @ Tknown.t()) scores every image against the entire known-class text matrix every step, not just the other 31 items in the batch. T_known is frozen throughout, matching "my text embeddings are fixed."

C correction: C is not ≈35,000. Re-derived directly from data/dl/label_train.json + all_classes.pkl with the exact split logic in the training script (rarest 20% of seen classes held out as an internal pseudo-unseen check):

17,393 total classes → 5,795 have any training images ("seen") → training holds out the rarest 20% (1,159 classes) as an internal validation proxy for the real unseen split → C = 4,636 known classes actually seen as softmax targets. This is Option 1 done correctly at the true scale, just an order of magnitude smaller than the number quoted in chat.

류.正.열 — "I will share the idea of plugging CosFace to train LoRA later."
✓ Drop-in — here's exactly where it goes, and why it's a different axis than what's already been tried

Because the loss already uses frozen text embeddings as the class-weight matrix, adding a CosFace margin is a one-line change to the same line shown above — subtract a margin from the target class's cosine before scaling, leave every other class's cosine untouched:

logit[i, y] = temp · ( cos(f_img, T_known[y]) − m )  // target class only
logit[i, j] = temp · cos(f_img, T_known[j])      // j ≠ y
loss = F.cross_entropy(logit, y)

temp=30 already plays CosFace's s. Sweep m ∈ {0.10, 0.20, 0.35} against the same pseudo-unseen db metric used for every LoRA variant below.

Why this is worth trying even though hard-negative mining already failed: hard-neg reweights which wrong classes count more in the loss; CosFace tightens the margin around the correct class regardless of which negatives are nearby. Different mechanism, not a rerun of the dead hard-neg probe (best db 14.06, below every other variant). The metric that actually decides deployment is not standalone db — it's the downstream fused-stack proxy gain against the +0.3 kill bar, exactly like v2 below.
